# AGENTS.md

This file guides AI coding agents (Claude Code, Codex, Cursor, Copilot and others) working in this repository.

## Overview

**Right On Cue** ("Emails that go out right on cue."), an email campaign scheduler in Python (Flask). The repo is `email_campaign_scheduler` and the Python package is `oncue`. The owner makes shows (campaigns), schedules them, and a background worker sends every email, retries failed sends, keeps to rate limits and tracks what happened to each one. The plan is `docs/PLAN.md`.

It is a learning project for **background jobs, retries, scheduling and rate limits**, so those parts stay easy to read: short comments that explain *why*, a job queue written by hand (no Celery, RQ or Redis), login written by hand (no Flask-Login), and no extra libraries unless the owner asks for them. Write the README in simple (A1-level) English.

Python 3.13 is at `%LOCALAPPDATA%\Programs\Python\Python313\python.exe`. Use the virtual environment:

- Install: `.venv\Scripts\python -m pip install -r requirements.txt` (create `.venv` with `python -m venv .venv` first if it's missing).
- First time: `.venv\Scripts\flask --app oncue upgrade-db` (makes the tables), then `.venv\Scripts\flask --app oncue create-owner` (your login; it asks for the password).
- Run: `.venv\Scripts\flask --app oncue run --debug --port 5013`, then open http://127.0.0.1:5013. (Ports: Swap Meter 5000, Ambon Alert 5001, Ang Gastos! 5002, Sangkap 5003, Gawi 5004, Akda 5005, Hire Wire 5006, Plan-It 5007, ShiroMoto 5008, DFJC 5009, Ticket Tock 5010, Tally Ho! 5011, J: Drive 5012.)
- Test: `.venv\Scripts\python -m pytest`. Every test gets a fresh SQLite file and never uses the internet. Set `TEST_DATABASE_URL` to an **empty** Neon branch to run the same tests on PostgreSQL (each test drops and remakes the tables). SQLAlchemy warnings fail the tests (`pytest.ini`).
- Other commands: `set-password <email>`, `worker` (a worker in its own window; Ctrl+C stops it after the job in hand; `--once` runs until nothing is due), `tick` (the timer once).

## Architecture

- **Accounts (`auth.py`):** no sign-up. The OWNER is made from the PC with `create-owner` (one per site); everyone else uses Try Demo. Hashes from Werkzeug; 5 wrong passwords lock the account for 15 minutes, one address may try 30 logins per 15 minutes (`limits.py`). `load_user()` checks `session_version` on every request (a password change logs out other devices) and puts `g.user` and `g.workspace` on the request.
- **Workspaces:** every row that belongs to someone has `workspace_id`. The owner's workspace is the real one; each Try Demo makes a sandbox workspace. Queries in views always filter by `g.workspace.id`.
- **Demo (`seed.py`, `views/demo.py`):** "Teatro Luna", run by Luna Reyes: 120 made-up contacts on `.example` domains (a few special practice addresses: `flaky.`, `slow.`, `busy.`, `bounce.`), lists, segments, scripts, shows to come, a weekly show and a their-own-time-zone show. Demo users have `.invalid` addresses, a random `session_version`, can't change their account, always use the practice mail server, and are deleted with their workspace after 24 hours (`seed.purge`, also by the timer). At most 100 demos at once, 10 per network an hour (not with `--debug`). **The demo's past is replayed, not written by hand:** `build()` (quick, in the Try Demo click) sets `workspace.replaying` and queues a `demo_history` job; it adds the past shows and runs `worker.simulate(..., workspace_id=...)` from 46 days ago to now through the real scheduler, queue, sender and practice server (the practice news is recorded straight after Sent instead of as jobs, `tracking.news_after_sent`), then stages one Unsure email and clears `replaying`. While `replaying`, `queue.in_scope()` keeps the live crew away from that workspace's jobs and shows. A show starts one minute before the visitor arrives (with a `busy.` address, so a Missed Cue is retrying) and another one minute after. The Stage shows a banner and reloads when the replay ends (`/stage/replay.json`). **Every page the demo can open must show an example, so add sample data with every new feature** (`tests/test_demo.py::test_the_replayed_past_fills_every_page` checks each page). Every foreign key needs an index starting with its column, because a demo's cascade deletes thousands of rows.
- **Audience (`audience.py`, `segments.py`, `csv_import.py`, `views/audience.py`):** contacts (email unique per workspace, first/last name, custom `fields` in a JSON column, own `time_zone`, `consent_at` + `consent_note`), tags (`contact_tags`), lists (`is_topic` lists show on the unsubscribe page), segments (rules turned into one SQL condition; custom fields through `Contact.fields[name].as_string()`, which works on SQLite and PostgreSQL; LIKE searches escape `%` and `_`; a List rule takes the list's name and stores its id), and the do-not-send list (`suppressions`: bounced, complained, manual). **`audience.eligible()` is the one rule for who may get an email: subscribed and not on the do-not-send list**; every audience (everyone, list, tag, segment) goes through `audience_condition()`. CSV import has four steps (Upload, Map Columns, Review, Done); the rows wait in `csv_imports`; Review counts exactly what Done will do; an import never subscribes an unsubscribed person again, and needs a consent tick.
- **Links in emails (`tokens.py`):** `tokens.make(purpose, *parts)` signs facts with an HMAC keyed by SECRET_KEY + purpose; `read()` / `read_ints()` return them only if untouched. Never change SECRET_KEY on the live site.
- **Unsubscribe (`views/public.py`):** `/u/<token>` (no login; leave topic lists, stop everything, or subscribe again) and `/u/<token>/one-click` (RFC 8058 one-click from mail apps, CSRF-exempt because the signed address is the proof). `public.on_unsubscribe` hooks run after someone stops everything.
- **Emails (`emails.py`):** `render(show_or_script, workspace, contact, ...)` gives (subject, html, text). Merge fields `{{field|fallback}}` are swapped for placeholders before Markdown (markdown-it, no raw HTML) and nh3 cleaning, then filled HTML-escaped, so a name can never become HTML or Markdown. Links only http/https/mailto; `link_wrapper` lets click tracking rewrite them. The email layout uses inline styles (mail apps ignore style sheets) and always has the unsubscribe link and the postal address. `unknown_fields()` points out likely typos.
- **Preview frames (`views/scripts.py`):** an email is shown in a sandboxed `<iframe name="preview">` from routes that send their own CSP (`FRAME_POLICY`: no scripts, inline styles only). The editor's Preview button posts the unsaved email there with `formaction` + `formtarget` (works without JavaScript); `app.js` presses it after a pause in typing.
- **Shows (`shows.py`, `views/shows.py`):** Rehearsal → Standby → Go → Curtain Down, with Hold/Resume and Cut (`ALLOWED`). Every change goes through `shows.move()`; pages post the `version` they showed, and `Show.version` is a SQLAlchemy `version_id_col` (optimistic locking: a stale save raises StaleDataError, which `save_or_conflict()` turns into a friendly ShowError). The worker uses `claim_status()` (a guarded UPDATE ... WHERE status = old) so two schedulers can't both start a show. Only Rehearsal and Standby can be edited; only Rehearsal can be deleted; anything can be duplicated. `problems()` lists what a show needs before Standby. `shows.on_move`, `views.shows.page_extras` and `views.shows.nudges` are hooks for later parts.
- **The job queue (`queue.py`), the background-jobs lesson:** a `jobs` table written by hand (no Celery/RQ/Redis). `enqueue()` (a UNIQUE `dedupe_key` makes the same work exist once; a savepoint catches a race), `claim()` (PostgreSQL `FOR UPDATE SKIP LOCKED`, plus a guarded `UPDATE ... WHERE status='queued'` checked by rowcount on both), leases (60 s, `heartbeat()`, `reap()` puts back a dead worker's job: at-least-once, so every handler must be safe to run twice), `Retry` (exponential backoff with full jitter, 30 s up to 1 h, or the service's Retry-After), `Defer` (wait without using a try), `GiveUp`, dead letters after `max_attempts` (6) with `retry_now()` / `discard()`. Handlers are registered with `@queue.handler(kind, on_dead=...)` and get `(s, job, now)`; their changes commit with the job's Done and roll back if they raise, unless they committed first on purpose. `run_job()` calls `s.expire_all()` first: a worker's session lives for many jobs, and a stale copy (a show still on Go after Hold) would be a bug.
- **The crew (`worker.py`):** a round = reap, `scheduler.run_due()`, `queue.work()`, heartbeat (`workers.last_seen`). A worker sleeps until the next due job / Standby show / lease (at most 30 minutes; polling every second would keep the free Neon database awake all day), and `nudge()` wakes the in-app worker early (Start now, Resume). The in-app thread starts on the first request (`RUN_WORKER`, off in tests); `flask worker` runs one in its own process. `simulate(s, start, until)` plays time forward from due moment to due moment without waiting: tests use it, and so does the demo.
- **Scheduler and fan-out (`scheduler.py`):** `run_due()` moves due Standby shows to Go with `shows.claim_status()` (only one worker wins), makes a `Performance` and queues `start_performance`. The fan-out handles 500 contacts per job (id order, `after_id`), makes `Message` rows (UNIQUE per performance + contact, so a batch done twice adds nobody twice) and queues a `send_message` job per message, then queues itself for the next batch. Hooks: `due_rules` (when one person's email goes), `on_start`, `batch_rules`.
- **Sending (`sending.py`, `mailers.py`, `practice_server.py`):** `send_message` looks again (Hold parks it, Cut cuts it, an unsubscribed or blocked person is Skipped), claims the message with a guarded UPDATE to On Stage and a fresh `send_token`, COMMITS, then calls the mailer and records Sent / Missed Cue (commits, then raises Retry) / Dropped. A message found On Stage means a send was in flight when a worker died: an idempotent mailer (the practice server, which keeps each `send_token` once) gets the same token again; any other mailer makes it Unsure, never a double email. When no message of a performance is open, the performance is done and the show goes to Curtain Down. Resume re-queues parked messages; Cut cuts the waiting ones. Every email has `List-Unsubscribe` + `List-Unsubscribe-Post` headers. The show page's meter is an SVG (widths are attributes, allowed by the CSP) that `app.js` updates from `/shows/<id>/progress.json` every 3 s while the show is on Go (or due within 10 minutes).
- **Sending limits (`buckets.py`), the rate-limits lesson:** checked in `sending.before_send`, all as `queue.Defer` (waiting never uses a try): the Safety Curtain (`breakers`: 10 failures in a row from one mailer close sending for 5 minutes, then one probe decides; bounces don't count), per-domain token buckets (`domain_limits`, emails a minute), the mailer's token bucket (`send_rate` a second; half speed for 10 minutes after a 429), and the daily cap (`send_counts`, one conditional `UPDATE ... WHERE count < cap`; UTC days like Brevo). Buckets change only by compare-and-swap (`UPDATE ... WHERE updated_at = <read> AND tokens = <read>`, retry on rowcount 0), so two workers never spend one token. `finish_estimate()` says when a big show will be out.
- **Mailers (`mailers.py`, `practice_server.py`, `brevo.py`):** answers are `Accepted`, `TryLater` (retry; 429 slows down), `Rejected` (`permanent_bounce` puts the address on the do-not-send list), or `MailerTimeout` (unknown). The `send_token` rule: a new token only after a clear "not taken" (TryLater clears it); after a timeout or a crash the token is kept, so the idempotent practice server answers "already have it", while Brevo (no idempotency key) makes the email Unsure. A demo always uses the practice server. The practice server is difficult at the rates in Settings (busy / timeout / bounce / slow, dice seeded by send_token + try, so tests use `CALM` rates from `conftest.py`) and special addresses always behave the same (`reject.`, `bounce.`, `complain.`, `flaky.`, `busy.`, `slow.`). Brevo's HTTP API (`BrevoMailer`, tested with a pretend `opener`). Send a Test goes through the same queue (`is_test` messages, 10 an hour).
- **Delivery tracking (`tracking.py`, `hooks.py`, `results.py`):** all news goes through `tracking.record()`: once (UNIQUE `source` + `event_id` on `message_events`), never backwards (it fills first-time stamps `delivered_at`, `opened_at`, ... and the status is worked out by rank from them; an open implies delivery), and with consequences (a hard bounce or a complaint puts the address on the do-not-send list; news about an Unsure email clears it up). Sources: Brevo's webhook `POST /hooks/brevo/<BREVO_WEBHOOK_SECRET>` (404 without the secret; finds the email by `message-id` or the `oncue-message-<id>` tag; answers 200 for anything it understood so Brevo doesn't retry), the practice server's planned news (`practice_event` jobs: delivered after seconds, about half opened within 45 minutes, a third of those click; `bounce.` and `complain.` addresses), our open pixel `/o/<token>.gif` (always answers with the picture) and click links `/c/<token>` (the token holds the `Link` id, never the URL, so it can't be an open redirect; 404 for a forged one), and the unsubscribe page. `results.py` counts from the stamps (delivered out of sent; opened, clicked and unsubscribed out of delivered). Pages: Results on a show, Every Email (`/shows/<id>/emails`, grouped tabs), one email's timeline, and Emails They Got on a contact.
- **Smart sending (`smart.py`, `views/callboard.py`):** hooks into the scheduler and sender. Their own time zone (`send_mode = "their_time"`, `local_date` + `local_time`): the show starts at the earliest such moment (UTC+14, `Etc/GMT-14`), `due_rule` gives each message its own `due_at` (contact zone, else the workspace's), and people for whom it has passed get it at once. Quiet hours (`workspaces.quiet_start/quiet_end`, minutes, may wrap past midnight) move a due time to the window's end and `quiet_check` defers a send that lands inside. The A/B subject test (`subject_b`, `ab_percent`, `ab_wait_hours`, `ab_metric`): `in_test()` hashes show + contact (the same split every time), others are "waiting", and the `ab_decide` job picks the winner by opens or clicks per delivered email (a tie goes to A) and releases them; not with weekly or their-time shows. Weekly shows (`repeat_days` like "0,3", `repeat_time`): when a performance finishes, `back_on_standby` moves the show to Standby at `next_occurrence()` (a missed time is skipped, never doubled). The Call Board pins a cue card per show per day, week and month views, on a plain dark board; a weekly show is ONE card in the Every Week lane at the top (its finished performances stay on their days); it stacks by day on phones. The show page schedules with one form: a When choice, and `app.js` shows only that choice's boxes (all of them without JavaScript). Dates and times: `dates.from_zone()` handles the daylight-saving gap and the repeated hour.
- **Reviews (`reviews.py`, `charts.py`, `views/reviews.py`):** a period (7/30/90/365 days) of emails SENT in it: the funnel, first opens per day (per week past 45 days, bucketed by the workspace's day in Python), bounce reasons, most clicked links, and show by show. Charts are SVG drawn on the server (`charts.columns()`, `charts.funnel()`): one series, one colour `--chart-bar` (#b45309 light / #cc7f1a dark, both checked with the dataviz validator against their surfaces; change both dark blocks together), no legend, rounded data-ends on the baseline, 2px gaps, whole-number ticks, x labels thinned so they never touch, a `<title>` hover label per bar and a table view.
- **Backstage (`views/backstage.py`):** the crew (workers seen in the last hour, with plain names like "Web app worker": on duty / gone quiet after 2 minutes / off duty; a demo replay deletes its own worker row; Start a Worker restarts the in-app thread when nobody is on duty), queue counts, Auto-pause (the Safety Curtain, with a plain "Resume sending now" button), Sending speed and the daily-cap gauge, Pause All Sending (`workspaces.sending_paused`, checked first in `sending.before_send`, a Defer so no tries are used), and the lists: Queue, Missed Cues, Dead Letters (Retry Now puts a Dropped email back in the wings / Discard), Unsure (It Went / Resend with a new token), and the Practice Inbox (each email in a sandboxed frame, with its headers and plain text). The menu badge counts dead letters + Unsure emails (`backstage_trouble`). The Stage shows a banner while paused or while the curtain is down.
- **The timer (`tick.py`, `.github/workflows/tick.yml`):** `POST /tasks/tick` with `X-Tick-Key` (404 otherwise) every 30 minutes wakes the site, runs worker rounds until nothing is due (25 s at most), deletes run-out demos and old CSV imports, forgets done jobs after a week and stopped workers after a day. On the free plan a show due while the site sleeps goes out at the next tick.
- **The words (`cues.py`):** the app talks like a theatre backstage (Show, Rehearsal, Standby, Go, Hold, Curtain Down, Cut, In the Wings, On Stage, Missed Cue, Dropped, Safety Curtain). Every cue word has a plain-English note; templates show them with the `cue()` / `show_status()` / `message_status()` macros in `_macros.html`, which put the note in a `title` and in hidden text for screen readers. Add new words to `cues.py`, never straight into a template.
- **Times (`dates.py`, `formatting.py`):** the database holds naive UTC. Pages show the workspace's time zone (Settings). Functions that decide something about time take the moment as an argument instead of reading the clock.
- **Database:** SQLAlchemy 2.0 ORM (typed `Mapped[...]`), plain (not Flask-SQLAlchemy). `oncue/db.py` makes one engine per app and one session per request: `db.session()`; code outside a request (the worker) uses `db.new_session()` and closes it. SQLite locally (`instance/oncue.sqlite`, WAL mode and a 30-second busy timeout so a worker and the pages can share it), PostgreSQL (Neon, psycopg 3) when `DATABASE_URL` is set. `workspaces` and `users` use `sqlite_autoincrement`, so a deleted demo's id is never handed out again.
- **Migrations: Alembic**, in `oncue/migrations/`. `flask --app oncue upgrade-db` runs them (with SQLite's foreign keys switched off during the run, so a table rebuild can't cascade-delete rows); Render runs it before gunicorn.
  - **To change the schema:** edit `models.py`, then `.venv\Scripts\alembic revision --autogenerate -m "what changed" --rev-id 000N`, **read the new file and fix it** (booleans default to `sa.false()`, never `sa.text('0')`, so PostgreSQL accepts them; a new NOT NULL column needs a `server_default`), and commit it. Never edit a migration that has run on the live site. `tests/test_migrations.py` fails if the models and the migrations disagree.
  - Every foreign key to a parent that is deleted in bulk needs an index that STARTS with that column, or the cascade scans the whole table.
- **Deploy:** `render.yaml` (service `right-on-cue`: one gunicorn process with 8 threads, so one in-app crew) + Neon + Brevo + the GitHub Actions timer; the steps are `docs/DEPLOY.md`. Environment: `SECRET_KEY`, `TICK_KEY`, `BREVO_WEBHOOK_SECRET` (made by Render), `BASE_URL` (the site's address, for links in emails), `DATABASE_URL`, `BREVO_API_KEY`. The owner is made from the PC with `create-owner` against Neon. Never change `SECRET_KEY` on the live site.
- **Every page works without JavaScript.** `app.js` only adds extras. The CSP (`__init__.py`) has no inline scripts or styles, so **never use `style=""` or inline `<script>`**: sizes and colours are classes.
- Commit messages and PR bodies go through files (`git commit -F`, `gh pr create --body-file`): PowerShell 5.1 breaks quotes in arguments.

## UI rules (the owner's priority is neatness)

- **Look: a theatre backstage**, drawn in CSS (no picture files), not just a palette: the velvet curtain (`.velvet`, the sidebar and the login panel, with a gold rope edge), the valance (`.valance`, scallops with a gold fringe along the top of every page), the stage floor (`.floor`, `--floorboards`, under page titles and empty states) with a spotlight (`.page-head::before`, `.spotlight`), marquee bulbs (`.marquee`, `.is-live` makes them chase; still for `prefers-reduced-motion`), the call board (`.corkboard`) with pinned cue cards (`.cue-card`), and gaffer-tape labels (`.tape`). Colours are tokens on `:root`: cream programme paper (`--bg` #f6efe3), plum-black ink, spotlight amber `--accent` #b45309 for buttons and links (white text 5:1; #f2a93b with dark text in dark mode). Cue stamps (`.cue-<tone>`) have a little cue light: Standby red, Go green, as on a stage manager's desk. Fredoka (rounded, "bubble") for headings, Nunito for text, Saira Condensed for labels, self-hosted in `static/fonts/`. Dark mode ("house lights down") is defined twice in `style.css` (device setting + the choice in Settings); change both blocks together (`tests/test_look.py` checks they match).
- Plain words for actions: buttons say what they do ("Resume sending now", "Update workspace"); themed words name states and places. The Brevo choice in Settings carries a red "Live: sends real emails" tag.
- **Messages are toasts** (`_toasts.html`, bottom right): `flash(msg)` is good news and fades after 6 seconds; `flash(msg, "error")` stays until closed; `flash(msg, "demo")` is the demo welcome (15 seconds).
- **Settings holds the controls, and the menus only navigate.** The theme (saved per device in `localStorage`; `theme.js` applies it before the page draws) is only on `/settings`. Log out is there too, and in the account menu at the bottom of the curtain.
- **No decorative emoji.** Icons are the line SVGs in `_icons.html`.
- **Page titles are bare:** `page_head(title)` from `_macros.html`, with no line of text under the title.
- **Title Case** for the menu, page titles (`h1`), section headings, tabs, empty-state titles and anything that names a page or a cue word. Small words (a, an, the, and, or, of, in, on, to, for, with, as, at, by) stay lowercase unless first. **Sentence case** for everything else: action buttons ("Save workspace", "Try the demo"), labels, hints, messages. The main button of a page is last on the right.
- Controls are the same height (`--control-height`) with bottoms aligned. Sizes in `rem`; the root font steps up at 1600 / 1920 / 2300px. Tabs are pills that wrap, never a sideways scroll; on phones, tables should fit rather than scroll.
- The curtain menu shows from 56rem up; below that a Menu button opens it.
- **Every PR must keep the README's pictures up to date (the owner's standing rule).** Screenshots live in `docs/screenshots/` and every one is shown in the README. If a PR visibly changes a page, retake the pictures with `docs/take_screenshots.py` (Playwright + Edge, borrowed from another project's `.venv`; its top comment has the steps; every picture comes from Try Demo, after its replay); if it adds a page or feature, add it there and a picture to the README. `tests/test_readme.py` fails if they disagree. In a PR description, link pictures with a full `raw.githubusercontent.com` address.
